# 真实评测报告（截至 2026-11-13）

本文只整理**已经发生过**的真实模型运行，数据来自各次数据库记录、运行记录文件与可信侧核验结论。
没有跑模型产生的新数据，也没有把构造的测试、桩件或独立校准当成一次模型尝试。凡是只在一侧核验过的
事实，都在文中标出来源；凡是无法复核的，直接写“未核验”，不补猜。

## 1. 统计口径先说清楚

样本单位是**一次正式尝试**，不是一个 Task，也不是一次“运行成功”。一次尝试要算通过，必须同时具备：
正式 Verification（`trusted_v1` / `passed`）、独立评测已校准、以及真人审核通过。缺任何一项都不能记通过，
只能记 `incomplete` 或相应的未完成标签。`incomplete` 不等于“补丁被验证为失败”——它表示这次尝试没有走到可判定的终点。

本文不给出整体成功率，原因在 §5 说明：两个任务的尝试次数、终止原因和记录形态都不同，
把它们压成一个百分比会掩盖差异，也会把一个受记录格式影响的筛选规则当成质量结论。

1,200 秒 / 80,000 token / 单次尝试 / 零自动重试，没有一次被放宽。

## 3. 通过的那一次，证据链长什么样

Click #3019 的第三次尝试（2026-11-12）是唯一一次走到终点并被人审通过的运行。可复核的环节依次是：

1. **任务与基线固定**：Task 绑定 40 位 base commit，Policy 快照 `benchmark-click3019-v1`，外部连接声明为 `none`
   （这是可信调用方的声明，不是系统对宿主网络的观测）。
2. **公开检查**：Verifier 在受控命令下对修改后的工作区跑公开 pytest 场景，结果 `passed`，并记录命令摘要与逐文件
   `public_tests_sha256`，供验收侧重算核对。
3. **独立评测**：可信侧用 `--network none` 的容器、私有 8 条随机化用例，先跑缺陷基准（failed）再跑参考版本（passed），
   校准通过后才评测本次补丁，得到 `passed` / `calibrated=true`，套件版本与草稿一致。
4. **正式验收**：`finalize_passing_verification` 在事务内重核执行权、工作区锁与命令证据后写入
   Verification `29e07087-…`（`trusted_v1` / `passed`），Run 变 `PASSED`，Task 变 `AWAITING_REVIEW`。
5. **人工审核**：真人在记录里写下 `accepted`，审核结论保存在审核副本与修正副本中。

这里有两个必须一起说的事实。其一，这次运行**先产生了一份字段自相矛盾的原始记录**（正式通过之后，
检查点输出被替换，分类器没有从正式 Verification 恢复字段），因此没有覆盖原文件，而是基于可信证据生成了
一份带 `correction` 链的修正副本；两份文件都在，原记录没有被改写。其二，人工审核结论**只存在于文件里**：
`task_reviews` 迁移已在隔离测试环境验证，但尚未应用到该案例所在数据库；数据库里该 Task 仍停在 `AWAITING_REVIEW`。

## 4. 未完成的那四次，分别停在哪

尝试 1 停在路由层：Supervisor 在 Explorer 汇报之后认为证据仍不足，要求继续探索，而此时模型预算已经不够，
输出 BLOCKED。它是一次真实的预算耗尽，不是代码异常。

尝试 2 已经走到补丁后 Verifier：公开初步结果 `passed`、草稿已提交、缺失项是 `test_integrity`，
Verifier 按设计保持 RUNNING 等正式评测结清。但阶段驱动先按 `status == RUNNING` 判定“未完成”，
`finalize_benchmark_run` 又用 `status == SUCCEEDED` 过滤候选执行，于是草稿既没被识别也没被交给 finalize。
这是本项目的接线缺陷，已经修复并补了回归测试；修完之后没有重跑，所以**这次尝试的记录保持 `incomplete`**，
也不回填成通过。

尝试 4 与尝试 5 是同一个任务（Click #3084）的两次尝试，都在多轮探索后因预算不足停止：
`src/click/core.py` 有 3,415 行，关键的 `Option` 定义在第 2,641 行附近。
尝试 4 里 Supervisor 反复要求补充证据，Explorer 先耗尽预算；尝试 5 里范围读取已经生效
（读到 1656–2555、2555–3415，第三次 2555–3004 是第二次的子集），关键定义确实被覆盖，
但多轮探索之后 Planner 拿不到剩余预算，直接抛 `PlannerModelBudgetUnavailableError`。
两次都没有产生补丁，因此**既不能说通过，也不能说补丁被验证为失败**。

## 5. 本文不宣称的结论

- 不宣称多任务成功率。一个任务通过、一个任务两次未完成，样本量不足以支持“稳定可用”或“成功率 X%”的说法。
- 不宣称 1/1。修正副本单文件汇总给出的 `1/1` 只描述那一份被选中的记录，不是全部尝试。
- 不宣称改动提高了效率。尝试 4→5 的总量几乎没变，尝试 1→2 的下降无法归因于代码，尝试 3 的用量低于前两次
  同样可能来自模型行为差异。
- 不宣称修复能保证下一次通过。触发条件被消除了（例如范围读取能读到关键定义），但预算如何在多轮探索中分配
  仍是一个未解决的设计问题；第三次尝试是否会通过，只能由下一次真实运行回答。
- 不宣称 `incomplete` 等于失败，也不宣称它等于“快成功了”。它只是没有可判定的终点。
- 不宣称独立套件或材料摘要证明了材料质量与隔离性。摘要只能标识“用的是同一份材料”。

## 6. 当前限制

**记录形态不一致。** 尝试 1、2 的记录生成于 `attempt_kind` 字段引入之前，读取时会被当作 `unknown`；
尝试 3 的原始记录是 schema V1，修正副本本身也不含 Task/Run ID，所以核对数据库时必须用本文第 2 节的 ID，
不能从缺失字段反推。这意味着用 `benchmark_record summarize` 的默认口径统计全部五份记录时，
只有尝试 3、4、5 会进入正式样本（样本 3、通过 1、未完成 2），而尝试 1、2 被排除的原因是**记录格式**，
不是因为它们不是真实尝试。任何引用这个比例的场合都必须同时说明这一点。

**审核尚未入库。** `task_reviews` 迁移（head `b7f2c31d8a90`）已在隔离测试环境验证，尚未应用到案例所在数据库；历史人工审核未回填，
审核人身份仍是自由字符串，改判未实现。因此“审核通过”目前是文件事实，不是数据库事实。

**两个任务的 Run 未关闭。** 尝试 1 与两次 #3084 尝试的 Run 在数据库里仍是 `RUNNING`，租约已过期但没有被关闭，
也没有被改写。这是有意保留：关闭或重跑属于需要授权的动作。

**来源限制。** Click #3084 的基准 checkout 来自第三方代理的浅仓库（沙箱到 github.com 不通），
commit 与 tree 已按 SHA-1 与 GitHub API 核对，但**不等于**可信 checkout。Click #3019 的参考材料取自
PyPI 8.3.1 wheel，控制端源文件与 wheel RECORD 一致，材料本身仍由可信侧保管。

**平台限制。** 受控 pytest 的 JUnit 报告采集依赖 Windows Job，非 Windows 上拿不到可用报告，
可信基线与正式验收无法在那里完成。也就是说，本报告里的正式结论都只能在 Windows 环境复核。

## 7. 只读复核方式

以下命令都不会调用模型、不会重新评测、不会改数据库：

```powershell
# 单份记录的汇总（只读记录文件，不代表整体统计）
uv run --locked python -m devflow_ai.benchmark_record summarize <记录路径>

# 逐角色用量与未结算请求（只读已提交的 llm_usage）
uv run --env-file <该次运行的数据库配置> --locked python -m devflow_ai.usage_report --run <RUN_ID>

# 两次尝试的逐角色差值
uv run --env-file <数据库配置> --locked python -m devflow_ai.usage_report --run <RUN_ID> --compare <RUN_ID>
```

记录文件位置（本机路径，换机器需要可信侧提供）：尝试 1 `benchmark-formal-7b5143ec…`、
尝试 2 `benchmark-second-fc4c7565…`、尝试 3 `benchmark-third-c59fb282…`（另有修正副本）、
尝试 4 `benchmark-3084-ad7156d7…`、尝试 5 `benchmark-3084-attempt2-8fab4a1b…`，都在
`D:/python/.devflow-test-temp/` 下。独立材料与隐藏用例不在仓库、不在本文、也不进入 Agent 上下文。
